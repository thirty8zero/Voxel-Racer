# Voxel Racer — content and systems reference

Last reviewed: 2026-10-08. Paths below are relative to the repository root.

This is a navigation and content-authoring guide, not a replacement for the current source or assets. Read `AGENTS.md` first. The user frequently changes tuning values in Unity: inspect the current asset before editing, and preserve unrelated values. Update this guide when adding a content family or changing a core workflow.

## Start here

- Unity version: `ProjectSettings/ProjectVersion.txt` (currently 6000.3.22f1). Rendering uses URP.
- Mobile is the rendering baseline: Quality Settings has `Mobile` (index 0) using `Assets/Settings/Mobile_RPAsset.asset`, selected for editor testing and the default for Android, iOS and standalone builds. Graphics Settings uses that same asset as its fallback. `PC` remains available for manual comparisons and is excluded from Android/iOS. The existing mobile asset uses 0.8 render scale, a 1024px main-light shadow map, one cascade, hard shadows and no SSAO renderer feature. Android is the primary active build target on the development editor; target selection is local editor state. Judge performance on an actual phone rather than editor FPS.
- Mobile post-processing: `Resources/MobilePostProcessingSettings.asset` is the master switch/profile reference; `Settings/MobilePostProcessingProfile.asset` starts with contrast +12, saturation +6, Neutral tonemapping, Dual quarter-resolution bloom (0.12 intensity, HQ filtering off, four iterations) and a 0.12 vignette. Tools > Voxel Racer > Post Processing > Enable / Disable saves the switch and refreshes live cameras; Select Settings exposes the same Effects Enabled checkbox and profile in the Inspector. The settings Inspector also refreshes live cameras. `VoxelMobilePostProcessing.Configure` is called by race, menu, car selection and garage camera setup; its idempotent scene-owned child global volume shares the profile without cloning it. Off sets camera `renderPostProcessing` false and disables the volume, bypassing the whole pass. No per-frame scene searches, depth texture effects, motion blur, DOF, SSAO or new renderer features. Create Initial Mobile Profile preserves existing profile/settings edits. Matching frozen Play Mode captures and integration report live under `Temp/PostProcessing/`; target-phone GPU performance is not established by those screenshots.
- Race lighting: `VoxelTrackEnvironment.ApplyLighting` uses the existing directional light (day intensity 1.3, warm RGB 1/.88/.72) and built-in gradient ambient: cool sky, neutral horizon and dim warm ground bounce. Night retains the track's key colour/intensity and uses `nightAmbientColour` for the sky, with darker scaled horizon/ground colours. No new lights, realtime reflection captures, renderer features or shadow settings. Shared Longtail paint, SpyCar2 alloy and metal-detail materials have restrained smoothness/metallic adjustments; these also appear wherever those materials are reused. Tools > Voxel Racer > Lighting > Render Day and Night Preview renders the real seeded Track01 road, SpyCar2, distant scenery and current mobile post-processing in an isolated temporary scene, restores material caches/RNG/lights and leaves source assets/gameplay state untouched. Captures: `Temp/LightingComparison/DayAfter.png` and `NightAfter.png`; the first-pass originals are `DayBefore.png` and `NightBefore.png`. Compare on-device GPU timing before claiming a performance result.
- Runtime scripts: `Assets/Scripts/`; editor builders, inspectors, previews and validation: `Assets/Scripts/Editor/`.
- Tunings/catalogues: `Assets/Resources/`. Authored models: `Assets/Prefabs/`, with boss assets also under `Assets/Resources/Bosses/`.
- Scenes in build settings: `Assets/Scenes/MainMenu.unity`, `CarSelect.unity`, `SampleScene.unity` (race), `RepairUpgrade.unity`.
- All runtime scene changes go through `VoxelLoadingScreen.LoadScene(buildIndex)`, using asynchronous single-scene loading under a persistent overlay; do not introduce direct `SceneManager.LoadScene` calls. It also shows at initial startup, covers destination Awake/bootstrap/Start, and stops departing scene roots immediately so old gameplay cannot change already-captured/reset state. It does not take the global clock. `VoxelStartCountdown` holds its opening fade/countdown/traffic/HUD until loading finishes. Menu/garage keyboard input and immediate-mode HUDs are gated while the overlay blocks pointer input above all game UI (canvas order 30000).
- `Resources/LoadingScreenSettings.asset` controls Show Images (currently off: plain black with the same white jiggling LOADING footer; the image list is retained for re-enabling), the editable random image list, minimum real display duration (initially 0.65s), top/bottom black bars and white LOADING font size. Initial pool: six textures from `Assets/Images`, excluding the two main-menu images. Three PNGs without filename extensions were given `.png` extensions while retaining their GUIDs. Main-menu texture references and null entries are always excluded at runtime, immediate repeats are avoided when alternatives exist, and image choice uses a separate RNG from gameplay. Empty lists produce black plus LOADING. Images fit between the bars without cropping/stretching; the bottom text jiggles on the real-time clock inside the safe footer, including at timeScale 0. Loading does not alter purchases, run damage, cash or campaign advancement; existing transition handlers retain those operations.
- Loading tools: Tools > Voxel Racer > Loading Screen > Select Settings / Render Example / Validate Transitions in Play Mode (start validation from MainMenu in Edit Mode). The settings Inspector has an explicit Replace List With Images Folder button; ordinary imports/edits never repopulate removed entries. Preview uses the same runtime view in a temporary preview scene and writes 16:9/20:9 examples plus animation frames under `Temp/LoadingScreen/`. Play validation covers startup and all four real scenes, persistent/input-blocking presentation, paused-time animation/minimum display, image exclusions/repeat/empty-pool handling, gameplay RNG/state isolation and countdown gating. Reports: `PreviewValidation.txt` and `PlayValidation.txt` in that folder.
- Race assembly starts in `VoxelRacerBootstrap.cs`. Many game objects and UI elements are created at runtime; a scene hierarchy alone is not the full implementation.
- Follow the existing blocky/voxel vehicle style, hollow body construction and mobile performance constraints.
- Retain `.meta` files/GUIDs. Prefer updating an existing prefab/asset over deleting and recreating it.
- Inspector convention: **vertical, independently expandable Odin foldouts**, with units, min/max pairs and conditional fields. Avoid horizontal tabs.
- DOTween is installed. Prefer it selectively for new presentation/UI work; existing gameplay movement and camera shake have their own controllers. Do not animate a transform concurrently with a controller that owns it.

## Player cars, damage and persistence

The primary player model is `Assets/Prefabs/Cars/SpyCar2PlayerCar.prefab`; its catalogue entry is `Assets/Resources/Cars/SpyCar2PlayerCar.asset`.

`VoxelCarSelectionState.LoadDefinitions()` discovers available `VoxelCarDefinition` assets from `Resources/Cars`, sorted by `selectionOrder`. Selection is stored by asset name in PlayerPrefs (`VoxelRacer.SelectedCar`). Without a matching saved selection, the first available entry is used. Renaming catalogue assets can therefore affect saved selection.

A car definition connects display name, selection availability/order, visual prefab, preview image and handling tuning. Player behaviour is **not all in VoxelCarTuning**: boost, weapons, upgrades, camera, mission rules and repair presentation have separate settings.

- `VoxelCarRunState`: damage and upgrade continuity between race and garage; `BeginNewRun` resets each upgrade family. Preserve hierarchy conventions used when capturing/restoring damage.
- `VoxelCurrencyState`: shared currency. Purchase through the upgrade state API, not by creating only a visual model.
- `VoxelCarController`: integrity, damage, lane movement, boost/ram offsets and effective driving stats.
- Player-requested lane changes (keyboard and touch) require `CurrentSpeed > 0`. At zero speed, requests are ignored and unfinished normal lane movement freezes; it resumes on movement without queuing stopped inputs. `AdvanceLaneChange` shares this speed gate with the request path. Collision recoil and oil spins keep their own motion. `VoxelBoostDrivingValidation` checks stopped left/right requests, positive-speed steering and partial-move freeze/resume.
- `VoxelCarBrakeLights.cs` is a controller partial that binds existing red rear lenses by the shared `CarMaterials/CarTailLights` material. Holding Space or the mobile brake swaps only those renderers to `CarMaterials/CarBrakeLights`, whose authored URP emission keyword keeps the red HDR glow available in Android builds. Release, pause, disabled driving/controller and destruction restore the original lenses; finish deceleration also lights them until stopped. Binding refreshes with integrity/model rebuilding, includes inactive damaged lenses and never reactivates them. Amber/white lamps, body materials, prefab assets and integrity remain unchanged. No extra lights, mesh pieces, per-frame hierarchy scans or material instances. Tools > Voxel Racer > Validate Player Brake Lights checks all catalogue models, damage/repair/material isolation and rear renders; Validate Player Brake Lights in Play Mode exercises the controller with controlled Input System Space/touch press/release and finish/driving gates. Reports and matching rear renders are under `Temp/BrakeLights/`.
- `VoxelIndestructiblePart`: marker on a part or ancestor excludes it from relevant destructible renderer scans. Keep structural chassis, engine and supports beneath this marker.
- `VoxelArmorVoxel`: armour hit points; `VoxelWheelIntegrity`: wheel damage constraints. Do not bypass these when adding damage sources.
- Armour voxels add to overall integrity; extra armour hit points do not simply become extra voxel counts. Left and right door armour are separate purchases.
- Prefer `CollisionTrackPosition` for vehicle interaction: raw `TrackDistance` alone misses player boost/ram offsets.
- `VoxelVehicleCollision.Sweep` handles fast relative motion. Preserve swept checks so boosting/reversing does not tunnel through targets.
- New damage sources should use `ApplyDamage` and a meaningful source label so mission breakdown and damage effects remain connected.
- Enemy health and per-voxel health are separate. Indestructible visuals must not keep a fully stripped boss alive; see `CheckBossBodyDestroyed`.

### New playable car recipe

1. Author a hollow visual prefab; keep +Z forward and use existing vehicle scale/conventions as the baseline.
2. Add structural parts beneath `VoxelIndestructiblePart`; avoid adding individual physics colliders to every voxel.
3. Create a `VoxelCarDefinition` under `Resources/Cars`, assign its prefab and handling tuning, and set availability/order.
4. Check selection, race creation, garage preview, integrity, damage restoration and all compatible upgrades.
5. Menu featured cars are a separate selection in `Resources/MainMenuTuning.asset`; adding a car catalogue entry does not automatically feature it there.

## Upgrade authoring — required workflow

**Every new car upgrade must appear and fit correctly in Tools > Voxel Racer > Upgrade Fit Preview.** This is a completion requirement in `AGENTS.md`.

| Guns | `VoxelGunTuning`, `VoxelGunUpgradeState`, `VoxelGunMount` | `Resources/Weapons/BasicHoodGunTuning.asset`, `LongBarrelHoodGunTuning.asset`; `Prefabs/Weapons/` |
| Wheel spikes | `VoxelWheelSpikeTuning`, `VoxelWheelSpikeUpgradeState` | `Resources/Upgrades/WheelSpikeTuning.asset`, `StarWheelSpikeTuning.asset`; `Prefabs/Upgrades/WheelSpike.prefab`, `StarWheelSpike.prefab` |
| Performance wheels | `VoxelPerformanceWheelTuning`, `VoxelPerformanceWheelUpgradeState` | `Resources/Upgrades/PerformanceWheelTuning.asset`, `Prefabs/Upgrades/PerformanceWheel.prefab` |
| Boost bottles | `VoxelBoostUpgradeTuning`, `VoxelBoostUpgradeState` | `Resources/Boost/BoostBottleUpgradeTuning.asset`, `DualBoostBottleUpgradeTuning.asset`; shared `Prefabs/Upgrades/BoostBottle.prefab` |
| Engine | `VoxelEngineUpgradeTuning`, `VoxelEngineUpgradeState` | `Resources/Upgrades/V6EngineUpgradeTuning.asset`, `Prefabs/Upgrades/V6Engine.prefab` |

1. Inspect the closest existing family, its loading path and purchase state. Several families use fixed `Resources.Load` paths or single purchase flags; a new asset does not automatically create another shop option.
2. Create a model prefab and tuning asset with price, compatibility, mounting and performance/damage fields.
3. Use a shared visual mounting helper for gameplay and preview. Preserve current local transforms, wheel pivots, exhaust ownership and gun muzzle positions.
4. Wire purchase button/card, affordability, owned/unavailable state, stats refresh and visual refresh into `VoxelRepairUpgradeSceneController` and relevant partial UI files. The shop currently has explicit cards; it is not the automatic fit catalogue.
5. Integrate run reset in `VoxelCarRunState.BeginNewRun`, and apply the upgrade wherever race/garage cars are constructed. Verify damage preservation during a purchase.
6. For a new family, implement `IVoxelUpgradeFitProvider` in `Assets/Scripts/Editor`. See `VoxelUpgradeFitCatalog.cs` and `VoxelEngineFitProvider.cs`.
7. A provider's `Discover()` returns entries with `Asset`, `Label`, `Fits` and `Build`. `TypeCache` discovers providers; `VoxelUpgradeFitCatalog.Assets<T>()` discovers assets. Do not add a hard-coded preview-window list.
8. Preview `Build` modifies only its supplied temporary car. Never spend currency, mark purchases, change run damage or edit source assets during preview.
9. Provide meaningful per-side/per-slot entries. Check isolated/combined upgrades, both sides, incompatible cars, body-hidden and upgrades-only views.
10. Run the relevant family validation and inspect the actual model from multiple angles.

Wheel spike side-ram damage is a percentage bonus (`sideRamDamageBonusPercent`, basic tuning currently +30%). `VoxelWheelSpikeUpgradeState.CalculateRamDamage` multiplies each enemy/boss tuning's `playerRamDamage` by `1 + bonus / 100` only for purchased side impacts; rear impacts stay unchanged. The legacy serialized field name migrates via `FormerlySerializedAs`. Radar traffic retains its existing instant-destruction collision behavior. Validate with Tools > Voxel Racer > Validate Wheel Spike Damage.

Star Wheel Spikes are a separate garage card with an independent `VoxelWheelSpikeTuning` asset (`Resources/Upgrades/StarWheelSpikeTuning.asset`, initially $400 / +50% side-ram damage). Each wheel gets a short centre spike surrounded by five longer square pyramids evenly spaced on a pentagonal ring. The detailed model adds flat beveled blade edges, stepped gunmetal sockets, steel lips and five hub fasteners; the outer spike centres sit on a 0.21m pentagonal ring, with splayed spacers seated into the hub. The builder bakes a 50% reduction of the complete model depth along local +X, anchored at its rear mounting face (x=0.145m), preserving every YZ coordinate, spike width and ring spacing. Outer tips now reach x=0.4525m and the centre tip x=0.2625m; wheel seating stays fixed. It remains one renderer, two shared existing metal materials, 780 triangles and no colliders. `upgradeLevel` controls replacement (basic defaults to 1; star is 2): buy stars directly or replace basics, never stack bonuses or allow repeat purchases/downgrades. A confirmation basket accepts only one spike variant. `InstalledTuning` survives race/garage transitions and `BeginNewRun` clears it with ownership. `VoxelWheelSpikeMount` identifies visuals; shared `CreateVisual` replaces a different variant, reuses an identical one and preserves the fixed wheel child name, protected integrity and performance-wheel centre offsets. The existing automatically discovered fit provider exposes All / Left / Right wheels for every spike tuning and keeps the highest level when variants are combined. Tools > Voxel Racer > Build Star Wheel Spike Upgrade updates only its prefab/mesh reference, preserving an existing tuning's price/damage/level edits. Validate Star Wheel Spikes checks actual shop preview/cancel/confirmation, direct/replacement purchases, affordability/duplicates, exclusive damage, body damage/integrity, persistence/reset, both performance-wheel install orders, compatibility/discovery and both-side isolated/combined/body-hidden/upgrades-only renders under `Temp/StarWheelSpikes/`. Validate Wheel Spike Damage checks all discovered spike variants against enemy/boss base damage. Tune the star independently through its asset's standard Odin Inspector and Open Upgrade Fit Preview button.

Dual Nitro Boost Bottles are a separate $1000 garage card in the Boost category, using `Resources/Boost/DualBoostBottleUpgradeTuning.asset`. It reuses the original right bottle and adds an identical bottle at the mirrored left rear-panel position through shared `VoxelBoostUpgradeState.CreateBottle` mounting. The left instance mirrors only its Protected Bottle Cradle across local X, so both cage braces reach inward to mirrored chassis anchors while the bottle and label keep their original orientation. Reapplying the shared helper sets the side explicitly, without flipping it repeatedly or editing the source prefab. Compatibility and per-charge performance start identical to the existing single-bottle upgrade. `bottleCount` (1–2) selects the capacity and replacement level: dual can be bought directly or replace single; duplicate purchases/downgrades and mixed single/dual pending baskets are blocked. `InstalledTuning` persists across races/garage and resets in `BeginNewRun`. The original right child name remains stable for damage paths; the left bottle has its own protected child. The discovered boost fit provider exposes both/left/right choices for dual without touching purchases or source assets.

`VoxelBoostController` tracks each charge independently: BOOST/Alt uses the next fully ready bottle, one burst can run at a time, and idle bottles keep recharging during another bottle's burst. Both charges start full on race Configure. Default/single upgrades retain one charge. `VoxelBoostDisplay` splits its existing 300-degree blue recharge ring into two 145-degree segments with a gap for dual; each segment shows its bottle's remaining burst or recharge independently, while the original button/touch area stays fixed. Tools > Voxel Racer > Validate Dual Boost Upgrade checks the shop preview/cancel/confirmation, affordability/replacement/persistence/reset, compatibility and both-side isolated/combined/body-hidden/upgrades-only fit, plus independent charge/HUD logic; output `Temp/DualBoost/Validation.txt` and renders. Validate Dual Boost in Play Mode checks actual pointer activation, pause, overlap rejection, recharge during the other burst and disable cleanup in a temporary empty scene; report `Temp/DualBoost/PlayValidation.txt`.

Engine exhausts belong to the engine. Each tip carries `VoxelEngineExhaustOutlet`; its local **+Z points out of the pipe**. Boost effects must use these outlets, including multiple outlets after an engine upgrade. Do not hard-code a single world-space flame position.

The V6 purchase also includes a slim, body-coloured rear wing with two short pedestals and gently drooping tips, styled after the reference spoiler. Its top is 0.16m above the 1.05m rear deck (half the original 0.32m height). `Prefabs/Upgrades/V6Engine.prefab` contains `V6 Rear Spoiler`, using `V6RearSpoilerMesh.asset` and the player's shared `LongtailPaint` material (one additional renderer, no colliders). It inherits the protected engine's integrity/damage behavior. The existing `VoxelEngineUpgradeState.CreateVisual` mounts the entire bundle for gameplay, garage pending previews and `VoxelEngineFitProvider`; ownership, compatibility, price, performance, exhausts and run reset remain the same. The shop card and confirmation identify the spoiler. Tools > Voxel Racer > Update V6 Rear Spoiler replaces only this child/mesh, preserving engine/exhaust/tuning edits; full Build V6 Engine Upgrade uses the same model helper. Validate V6 Engine Upgrade checks confirmed purchase, free preview, compatibility, duplicates, next-mission persistence, reset, body damage/integrity and exhausts, then renders isolated/combined/body-hidden/engine-only fit from both sides, rear and top under `Temp/V6Spoiler/` (Edit Mode).

## Tracks, traffic and enemy variants

- Road Tuning > **Road Horizon** exposes `horizonRoadEnabled` and `horizonRoadDistance` (default 760m, range 100–1000m). `EndlessVoxelRoadHorizon` is a partial of the existing controller: one reusable mesh/renderer, three material submeshes for asphalt/shoulders/markings, no collider or shadow work, and no extra traffic. Three owned material instances retain the current surface colours/asphalt patches. Asphalt uses the build-referenced `Resources/Scenery/RoadHorizonSurface.mat` / `VoxelHorizonRoad.shader` and dithers away between 62% and 94% of the horizon distance. White edges/yellow markings clone their original source materials and continue to the full horizon, retaining their original lighting/fog behavior. Only the distant paint widens subtly with distance (minimum width 0.0012 times the track distance from the player) to remain readable below pixel scale. It stays on the actual world-space surface; nearby detailed paint and road widths remain unchanged. Native materials share the mesh lifecycle and clone ownership rules. It samples the real future path with the existing deterministic turn generator; enabling it does not consume gameplay RNG or change the route. The last three detailed chunks overlap a 0.025m-lower underlay so recycled chunks can fade in without holes. Coverage rebuilds at chunk/coverage boundaries, with no warmed per-frame allocations. Cache/seed rebuilds invalidate the shape, preview clones do not own the source mesh, destruction releases it, and finish preservation freezes it along with the existing road.
- The existing single continuous ground box expands to cover the horizon road plus a two-segment margin, without adding geometry or changing `groundWidth`'s scenery coverage/density budgets. Existing nearby road surfaces, colliders, lane widths, camera settings and track seeds remain authored values. Existing 520m horizon defaults are now 760m; existing 320m track fog endpoints are now 720m so the smaller distant road stays visible before fading. Other authored values are preserved. Existing road tuning assets/subassets serialize the new controls independently.
- `VoxelMountainCard.shader` and `VoxelHorizonSun.shader` preserve projected artwork position/size but write ordered background depth: world geometry in front, mountain cutouts next, sun/moon behind them. This prevents the old 170m mountain ring from acting as a wall that cuts off the road. The hidden `_HorizonBackground` shader switch exists for the comparison renderer's original-depth before view; normal materials default to background rendering.
- `VoxelDistantSceneryHorizon.cs` extends the existing instanced scenery renderer with the same 16 four-triangle bush/grass cards and shared atlas, without extra GameObjects, meshes, colliders, shadows or 3D cactus populations. Stable 32m tiles cover a 288m-wide strip around the real path ahead and behind the player; tile/frustum/distance culling and 1023-instance batches keep streaming bounded. Ground Cover > **Road Horizon Ground Cover** exposes enable and clumps per tile (48 initially). The layer crossfades in over the existing nearby foliage fade interval (110–150m) and out over 65–95% of Road Horizon distance. Nearby foliage retains its authored density, scales and patches. A path revision invalidates the extension cache after road rebuilds; gameplay RNG is untouched. **Validate Ground Cover** checks distant population, bends/road clearance, unchanged close scenery, deterministic rebuilds/RNG, zero cached-refresh allocations, streaming/cleanup and shaders. Report/comparison renders: `Temp/RoadHorizonScenery/`.
- Tools > Voxel Racer > Road Horizon > **Render Before and After** uses the same seeded Track01, real chase Camera Tuning/FOV, player, scenery and mobile profile for day/night 1920×1080 captures under `Temp/RoadHorizon/`. Only the horizon extension/ground coverage, horizon billboards and backdrop depth differ; these are isolated Edit Mode renders, not live gameplay screenshots. **Validate** covers every authored road and tight bends, joins, unchanged detailed geometry/colliders, three-batch budgets, RNG, zero cached-refresh allocations, chunk handoffs, toggling, clone ownership, seed rebuild and native cleanup. **Validate in Play Mode** covers real Update-driven recycling, mesh reuse, finish freeze and deferred cleanup, returning to the original editor scene. Reports: `Validation.txt` and `PlayValidation.txt`. Horizon-sun validation uses controlled cloned day/setting fixtures and individual authored day/moon settings, allowing mixed/reordered campaigns, and checks mountain/sun/world depth ordering.

New tracks must be assigned to the ordered `tracks` array in `Assets/Resources/VoxelTrackSequence.asset`. Creating an asset under `Resources/Tracks` alone does not add it to the campaign. `VoxelTrackProgressState` handles sequence position and advancement; the sequence has a loop option.

`VoxelTrackDefinition` references road, traffic and mission tunings plus environment and optional boss settings. Its custom editor maintains embedded road/traffic subassets and legacy migration. When duplicating tracks, verify which tunings are embedded versus shared; do not unintentionally edit another track through a shared reference.

Road positions use lane offsets and distance along `EndlessVoxelRoad`/`VoxelTrackPose`. World Z is not a substitute on turning roads. Current lane count comes from road tuning; dynamically appearing/disappearing lanes were discussed but are not an established implemented system here.
The continuous outer road shoulders are 0.55m wide (half the original 1.1m), placed flush against the asphalt edge; all current tracks and the fallback/new-track palette use white shoulders. Track shoulder colour/material overrides remain supported. White shoulder materials suppress the dashed outer road markers; coloured shoulders retain their original 0.18m markers, sharing the road-line material. Yellow interior lane dashes remain visible. Shoulder height, segment lengths and marker spacing remain unchanged. Mission starts have no painted transverse start line; the opening fade/countdown and finish sequence remain. Generated environment layout version 26 rebuilds older cached geometry with joined road surfaces.
Asphalt and both shoulders use `VoxelRoadStripMesh`: three closed meshes/renderers/static MeshColliders per road chunk, sampled at the existing curve slice boundaries. All three strips share the same cross-sections and neighboring chunks share their end frame, closing inside/outside corner gaps without overlapping box slices. Widths and surface heights remain unchanged. Asphalt UVs carry lateral metres and absolute track distance (`_UseRoadUV` on the renderer property block); the shader retains its legacy cube-coordinate path for other users and fade-in restores the property block. Each strip owns/releases its generated mesh on recycle/rebuild/destruction; preview clones share the mesh without taking ownership. Tools > Voxel Racer > Validate and Render Road Shoulder Joins checks straight/tight consecutive bends and all authored tracks, shared slice/chunk edges, collision coverage, UV continuity, normals, renderer/triangle budgets, cache rebuild and mesh cleanup, with matching before/after captures and report under `Temp/RoadShoulders/`.

Track > Road > Turning Road Pieces uses `turnSeed` to reproduce the generated turn sequence when the other road settings and starting point match. Enable `randomizeTurnSeedEachRun` to choose a fresh seed when the runtime road is first built; that selected seed is reused if the road rebuilds during the same run. The authored seed remains visible but disabled while randomization is enabled. Edit Mode previews continue to use the authored seed.

### Civilians

- `VoxelObstacleCar` owns driving phases, collisions, near misses and civilian damage behaviour.
- `CivilianHatchback.prefab`, `CivilianTransitVan.prefab`, `CivilianBeetle.prefab`, `CivilianKombi.prefab`, `CivilianJetta.prefab` and `CivilianMercedesWagon.prefab` live in `Assets/Prefabs/Cars/`. The Beetle uses a hollow stepped shell, shared civilian paint/trim materials, four animated wheel roots and TrafficCar durability copied into `CivilianBeetleTuning.asset`.
- All six civilian prefabs have an `Indestructible Civilian Driveline` group marked with `VoxelIndestructiblePart`: two axles aligned to the actual wheel centres and one connecting shaft (three extra pieces per car). ### Spike slam

`VoxelEnemyCarSpikeAttack.cs` is a partial of `VoxelEnemyCar`; `VoxelBossSpikeRig` animates rear door hinges and the triple spike slide.

Sequence: Normal → Warning (doors open 180°, spikes extend; mines already disabled) → Braking → Holding on a miss → Retreating → Normal. A spike hit jumps immediately to Retreating. A player side ram enters Retreating after `sideRamRetreatDelay` (0.1s by default). Lane choice stays locked during the attack so dodging is meaningful.

- Closing speed is relative to player speed and permits actual reverse motion during the slam. `spikeAttackClosingSpeed` caps it; `spikeAttackClosingResponse` controls approach response; braking and acceleration control speed changes.
- On a miss, `spikeAttackMissDistance` determines how far back to come (0 = alongside). A timeout still prevents a stuck approach.
- Swept collision detects fast hits. Post-movement body clearance keeps bodies separate even during boost/reverse movement; only spikes may intersect the player.
- One hit per attack, tunable voxel damage, source label Boss spike ram. `VoxelSpikeImpact` adds a large mesh-particle debris burst.
- Spikes retract and doors close together from retreat start. Normal behaviour resumes only once retreat distance is reached and the rig is closed.
- Attack interval resets after retreat ends. Chance rolls and lane-settling may delay the next attack; failed rolls wait another interval.
- Mines stay disabled through all attack stages and resume with a delay after retreat.

The full `VoxelRedVanBossBuilder.Build()` recreates the visual from the civilian van and also touches track/sequence configuration; inspect its side effects before running it.

Rear eyes are red pixel geometry baked into existing glass voxel meshes, with a second material. They follow door damage/rotation without adding damage targets. `VoxelBossEyesBuilder` controls placement; use mesh APIs (`Clear`/`CombineMeshes`) to rebuild existing meshes so rendering updates reliably. ### Unity MCP notes

Discover available Unity tools rather than assuming a prior connection. `Unity_RunCommand` accepts `Code` and `Title`; code must implement an **internal** `CommandScript : IRunCommand` with `Execute(ExecutionResult result)`.

Call compiled editor helpers for complex checks. Dynamic MCP snippets may not resolve Odin editor assemblies directly; putting that work in a compiled editor helper avoids this. Fully qualify `UnityEngine.Mesh` in snippets if a tool namespace shadows `Mesh`.

Unity MCP often temporarily disappears during script recompilation. Wait briefly and retry; if it remains unavailable, ask the user to focus Unity and refresh assets. Do not report prefab generation or Unity validation as complete merely because source files were written.
